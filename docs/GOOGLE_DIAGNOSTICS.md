# Google connection diagnostics

The repair uses typed Google `ErrorInfo` reasons before legacy reasons and never guesses from a message containing "is disabled". Unknown errors stay generic. Quotas, missing Calendar scopes, invalid authorization, project restrictions, policy restrictions, missing calendars and temporary failures have separate host guidance. Refresh-token rejection differs from an application OAuth configuration failure or a temporary network failure.

`GET /api/google/status` remains authenticated and always checks the signed-in user's own connection. It returns only validated, allowlisted reason/domain/service/consumer identifiers. It ignores query parameters attempting to select another host. Public endpoints return a generic availability error; server logs contain only HTTP status and the normalized code. Raw Google messages, arbitrary metadata, Help URLs, tokens, client secrets, calendar identifiers and busy contents are never diagnostic output. Responses are `Cache-Control: no-store`.

An enablement link is returned only when Google supplies a typed, trusted disabled-service reason, service `calendar-json.googleapis.com`, and a syntactically valid `projects/<number-or-id>` consumer. The application constructs a fixed Google Console URL with that reported project; it never copies a provider-supplied URL, guesses from the OAuth client, or links to the console's default project. This establishes which project Google reported for that request, not whether the viewer owns it or whether it is currently enabled. Without those fields, the host sees instructions to compare the exact deployed OAuth client/project.

The patch changes no schema, credentials, OAuth grants, stored tokens or project settings. A successful later check clears the displayed diagnostic/link. It does not bypass Google availability checks or establish the current production root cause. [Google's reason/metadata definitions](https://docs.cloud.google.com/php/docs/reference/common-protos/latest/Api.ErrorReason) distinguish disabled services from suspended consumers, billing restrictions and quotas; [Calendar's error guide](https://developers.google.com/workspace/calendar/api/guides/errors) also documents quota-related HTTP 403 responses.

Before deployment, reconcile current production backup readiness and authenticated Render access. The separate proposed project move has additional requirements documented in [Google project migration](GOOGLE_PROJECT_MIGRATION.md).
